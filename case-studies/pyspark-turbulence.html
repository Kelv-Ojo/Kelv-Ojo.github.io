Exploring turbulence modelling with PySpark

A case study drawn from my 7153CEM Big Data Analytics and Data Visualisation coursework. It documents the reported approach and what I would verify before relying on the results.

The analytical question

Can a distributed processing workflow prepare computational fluid dynamics data and compare regression models for turbulent kinetic energy?

Work described in the report

  • Load and inspect the komegasst.csv simulation dataset using Spark DataFrames.
  • Investigate sparsely populated wall-function variables rather than treating their missing values as ordinary measurements.
  • Assemble velocity components, specific dissipation rate, pressure and turbulent viscosity as predictors.
  • Compare a linear regression baseline with a Random Forest regressor, then export prediction errors and feature rankings for Tableau visualisation.

Reported findings

The report describes 902,812 observations. It reports Random Forest R² of 0.9889 and RMSE of 0.1702, compared with linear regression R² of 0.0919. These values have not been regenerated in this portfolio review. R² is a regression fit metric; it is not classification accuracy.

What needs checking

The local report draft gives conflicting column counts, predictor counts and timing descriptions. The original Spark notebook, input dataset and Tableau workbook were not recovered for this review. The portfolio therefore makes no verified runtime, speed-up, cluster-scale or deployment claim.

Random row splits can place related spatial observations from one simulation in both training and test sets. A stronger evaluation would hold out complete flow cases or spatial regions, fit learned transformations on training data only, and compare errors by case. Feature availability and physical relationships also need review to rule out target leakage.

Why this belongs in my portfolio

It adds experience with Spark DataFrames, regression evaluation and communicating large simulation datasets. The useful judgement is recognising that a high reported score needs a credible validation design and reproducible inputs before it can support an engineering decision.

Next development step

Recover the original pipeline and input snapshot, reconcile the schema and timing logs, and rerun against a case-based holdout. Performance benchmarking would need a documented machine, workload and comparable single-process baseline. These are proposed improvements, not completed results.

Interview questions

  • Why might random row splitting overstate performance on simulation data?
  • What evidence would establish that Spark improved runtime?
  • Why is R² not the same as prediction accuracy or engineering reliability?

Recommendation and success measures

Proposed action — Reproduce the reported analysis and validate on held-out simulation cases.

How I’d measure success — Compare prediction errors against a simple baseline across unseen cases; coursework scores remain unverified until rerun.

These are proposed next steps, not implemented outcomes.
